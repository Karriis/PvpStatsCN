# pvplogs 战绩平台与玩家身份系统实施计划

> 状态：首版已实现，进入发布配置与联调阶段
> 更新日期：2026-08-26
> 说明：前端视觉、页面布局与交互方案见 [pvplogs-frontend-plan.md](./pvplogs-frontend-plan.md)。

## 0. 实施结果与后续决定

- 当前代码按工作区拆分为 `D:\Codex\pvplog\pvplogs-web` 与 `D:\Codex\pvplog\pvplogs-api`，PvpStatsCN 插件继续独立维护于本仓库。
- 按用户后续决定不制作 Docker；开发环境使用项目专用 PostgreSQL 16，生产基线采用 systemd、Nginx、PostgreSQL 备份和隔离导入单元。
- HMAC、设备绑定、三种玩法、关键时间线、80% 多来源合并、身份加密、UsedName 增量观察、账号级隐私、TOTP、软删除、隔离导入和后台治理均已实现并通过自动化测试。
- 对局上传的实际统一入口为 `/api/v1/plugin/uploads`；`/plugin/identities` 保留为独立增量身份同步入口。
- 正式上线仍需由部署方提供域名、TLS、生产 PostgreSQL、SMTP 和独立生产密钥；这些外部配置不写入仓库。

## 1. 总体架构

- 新建私有仓库 `pvplogs`，与 PvpStatsCN 插件仓库独立发布。
- 网站仓库包含：
  - `apps/web`：Next.js App Router、React、TypeScript。
  - `apps/api`：Go、chi、pgx、sqlc、PostgreSQL。
  - `services/litedb-importer`：隔离的 .NET LiteDB 解析工作器。
  - `infra`：Docker Compose、反向代理、备份及部署配置。
- 前端采用 Tailwind CSS、shadcn/ui、Framer Motion，并复制 [TripleD UI](https://github.com/moumen-soliman/uitripled) 组件到本项目维护。
- 简体中文首发并预留 i18n；品牌、配色、字体和具体页面设计后续确定。
- 公开端完整响应式，后台桌面优先。
- 单台 VPS + systemd、Nginx 和 PostgreSQL 起步，部署地区保持可配置；不制作 Docker。

## 2. PvpStatsCN 身份采集模块

### 2.1 UsedName 依赖与身份适配

- PvpStatsCN 将 UsedName 声明为插件依赖，通过独立适配层读取它能够稳定提供的身份与曾用名数据。
- 后端上传协议不依赖 UsedName 的内部存储格式；适配层必须转换为本项目定义的版本化身份观察 DTO。
- UsedName 暂时不可用、版本不兼容或没有对应身份记录时，战绩采集与上传仍可继续，曾用名数据标记为缺失。
- 不复制 UsedName 源码；若当前版本没有稳定 IPC/API，则先保留适配接口并继续使用 PvpStatsCN 自身从 PvP 结算包读取的 Account ID、Content ID、角色名和服务器信息。
- 身份归并遵循以下核心规则：
  - Account ID 标识游戏账号。
  - Content ID 标识具体角色。
  - 同一 Content ID 出现不同名称或服务器时记录为改名或转服。
  - 同一 Account ID 下的多个 Content ID 归入同一个公开玩家档案。
- UsedName 只作为身份补充来源，不能作为玩家唯一身份依据，也不能绕过 Content ID、Account ID 和来源可信度校验。

### 2.2 采集范围

- 后台监听能够可靠提供 Content ID 的社交列表：
  - 小队、好友、通讯贝、部队成员。
  - 玩家搜索、原服务器在线成员、部队申请。
  - 新人频道、导师、回归者及其他已确认结构的列表。
- 三种 PvP 结算包同时采集所有参赛者的 Account ID、Content ID、角色名和服务器。
- 不复刻 UsedName 的昵称、搜索、订阅、右键菜单和曾用名 UI；该模块没有用户可见管理界面。
- 每次观察保存：
  - Account ID，可为空。
  - Content ID，必须有效且非零。
  - 角色名、服务器 ID。
  - 来源列表、首次与最后观察时间。
  - 游戏版本、插件版本、结构解析版本。
- Account ID 缺失时先建立角色级身份；以后获得可靠 Account ID 时再挂入账号档案。
- 所有客户端内存结构均进行版本验证。偏移、人数或 ID 合理性验证失败时，自动停用对应来源，不能把可疑 ID 写入身份库。

### 2.3 本地持久化和同步

- 在现有 `data.db` 中新增独立集合：
  - `playeridentity`
  - `playeraliasobservation`
  - `identitysyncstate`
- 用户首次启用网站上传时展示一份完整使用协议，一次性明确说明：
  - 上传整场 PvP 数据会包含其他参赛者。
  - 插件会同步社交列表中观察到的玩家身份与曾用名。
  - 身份记录可能属于未安装插件的玩家。
  - 玩家可以申请全站匿名化。
- 用户确认协议并开启自动上传后，战绩和身份观察使用同一上传授权，不设置第二个开关。
- 用户未确认协议时，两类云端同步均保持关闭。
- 身份观察分批、增量上传；同一观察记录使用幂等键，避免重复同步。
- 所有已观察玩家身份均可上传云端，但没有公开 PvP 对局的玩家不生成公开页面、不能被搜索。
- 曾用名默认不公开展示，也不能作为公开搜索关键词，仅用于身份归并、后台审核和匿名化覆盖。

## 3. 战绩、身份与隐私模型

### 3.1 战绩数据

- 支持水晶冲突、纷争前线、烈羽争锋。
- 上传完整结算和关键结构化时间线：
  - 水晶冲突：水晶进度、击倒、极限技关键事件。
  - 纷争前线：队伍积分和本人战意变化。
  - 烈羽争锋：建筑、机甲、飞翔层数、佣兵和资源事件。
- 不上传聊天、调试日志、内存快照和逐技能原始遥测。
- 每场公开对局生成 ULID；插件本地 ObjectId 只作为来源标识。
- 多人上传同一场时，通过模式、地图、时间、结果和参与者重合率自动合并；参与者重合达到 80% 且结果一致才可自动合并。
- 原始来源不可修改；管理员只能隔离、切换可信来源或重新执行合并。

### 3.2 玩家身份结构

```text
GameAccount
├─ Account ID 密文
├─ Account ID HMAC 索引
└─ Characters
   ├─ Content ID 密文与 HMAC 索引
   ├─ 当前名称 + 当前服务器
   └─ AliasObservations
      ├─ 历史名称 + 历史服务器
      ├─ 首次/最后观察时间
      └─ 数据来源
```

- Account ID 与 Content ID 均字段级加密保存，并额外生成不可逆 HMAC 检索索引。
- ID 不得出现在公开 API、URL、日志、错误信息或后台普通列表中。
- 公开档案以 Account ID 聚合，因此同一账号的小号会显示在同一玩家档案中。
- 曾用名和历史服务器默认仅后台可见；公开端只显示当前角色列表及其战绩。
- 只有账号至少参与一场公开对局后，才生成可搜索档案。
- 公开查询支持：
  - 对局公开 ID 精确查询。
  - 当前角色名 + 当前服务器查询玩家档案。
- 首页只展示匿名全站汇总，不展示最近玩家、个人排行榜或热门玩家。
- 玩家档案、搜索结果和对局详情统一设置 `noindex`。

### 3.3 匿名化与删除

- 玩家通过网站提交人工匿名化申请、角色信息、理由和证明材料。
- 审核通过后默认覆盖该 Account ID 下所有已确认角色：
  - 关闭公开玩家档案。
  - 从搜索结果移除。
  - 对局详情使用匿名占位名称。
  - 团队和全站匿名统计继续保留。
  - 曾用名和纯身份观察记录不再公开参与任何关联。
- 证明材料结案后默认保留 90 天再物理删除。
- 账号或对局删除采用 30 天软删除恢复窗。
- 上传账号注销时撤销全部令牌并删除账号资料；已验证公共对局继续保留，来源改为内部匿名编号。

## 4. 网站账号、导入与后台

### 4.1 网站账号和插件绑定

- 公开查询无需登录。
- 上传者使用邮箱、密码和邮箱验证注册。
- 网站生成短时绑定码，插件兑换可撤销的设备令牌。
- 一个账号可以绑定多个设备和角色；首版不限制数量，后台保留限制设置。
- 密码使用 Argon2id；设备令牌只保存哈希。
- 管理员和审核员强制 TOTP 双因素认证。

### 4.2 `data.db` 导入

- 普通用户不能在网站上传 `data.db`；只有管理员可在后台上传 PvpStatsCN 或原版 PvpStats 的历史数据库，并且必须指定现有目标角色与来源说明。
- Go API 将文件写入随机隔离临时目录，再交给无网络、低权限、只读输入的 .NET Worker。
- Worker 使用官方 LiteDB 库，只读取白名单集合并输出规范化 NDJSON。
- 新版 PvpStatsCN 数据库中的身份集合也可导入；原版数据库没有身份集合时，只导入战绩。
- 默认限制：
  - 文件最大 256 MiB。
  - 每账号一个并发导入任务。
  - 解析超时 5 分钟。
  - Worker 内存上限 512 MiB。
- 无论成功或失败，解析结束立即删除原始文件。

### 4.3 管理后台

- 管理员权限：
  - 用户、设备、令牌和上传风控。
  - 对局、来源、冲突、隔离和重新合并。
  - Account ID、Content ID、角色和曾用名关系。
  - 身份观察记录和异常 ID。
  - 隐私申请、匿名化、恢复和删除。
  - 导入任务、系统配置和审计日志。
- 审核员权限：
  - 隐私申请、举报、异常对局和必要证明材料。
  - 不能管理管理员、系统密钥或修改审计记录。
- 所有敏感查看、合并、拆分、匿名化、恢复、删除、封禁和令牌撤销均记录审计日志。
- 管理员不能手工编辑伤害、击杀等战绩数字。

## 5. API 设计

- `/api/v1/auth/*`：注册、邮箱验证、登录、找回密码和会话。
- `/api/v1/plugin/bind`：一次性绑定码兑换设备令牌。
- `/api/v1/plugin/matches`：结算与关键时间线上传。
- `/api/v1/plugin/identities`：身份观察增量同步。
- `/api/v1/admin/imports`：管理员上传和查询绑定目标角色的 `data.db` 导入任务。
- `/api/v1/public/matches/{publicId}`：公开对局详情。
- `/api/v1/public/players/search`：角色名与服务器查询。
- `/api/v1/public/players/{publicId}`：账号级玩家档案。
- `/api/v1/admin/*`：后台治理、审核、身份关系和审计。
- 插件上传使用版本化 JSON、gzip、每安装实例独立密钥、HMAC-SHA256、内容哈希、时间戳、Nonce 和幂等键。

### 5.1 HMAC 上传签名

- 网站绑定插件后，为每个安装实例生成独立 `installation_id` 和密钥版本。
- 服务端使用主密钥、安装实例 ID 与密钥版本派生安装密钥；主密钥只存在于环境变量或密钥管理系统。
- Windows 客户端使用 DPAPI 加密保存自己的安装密钥。
- 签名原文固定包含：协议版本、HTTP Method、请求路径、安装实例、绑定账号、密钥版本、Unix 时间戳、Nonce、插件版本、Schema 版本、客户端构建哈希、Idempotency-Key 和原始请求正文 SHA-256。
- gzip 请求的正文摘要针对实际传输的压缩后二进制计算。服务端先验签，再解压和解析 JSON。
- 服务端允许前后最多 5 分钟时间偏差；Nonce 至少保留 10 分钟；所有签名比较使用常量时间比较。
- 禁止使用 `SHA256(正文 + 盐 + 私钥)` 形式的自定义签名，密钥只能作为标准 HMAC 的 key。
- HMAC 只能证明请求来自已登记实例且传输中未被修改。持有合法密钥的篡改客户端仍需通过数据逻辑校验、多来源交叉验证、来源风险评分与吊销机制处理。

## 6. 测试范围

- 三种 PvP 结算包的 Account ID、Content ID、角色名和服务器解析。
- 所有社交列表来源的结构验证、零值过滤和版本失效保护。
- 同一 Content ID 改名、转服后的历史记录。
- 同一 Account ID 多角色的账号级合并。
- Account ID 缺失后补全、错误身份拆分和冲突隔离。
- 身份观察上传后，无公开战绩玩家不能被搜索。
- 曾用名不能通过公开搜索、接口或页面泄露。
- 重复对局合并、冲突来源和上传重试幂等。
- 匿名化覆盖全部角色、曾用名和历史对局。
- 损坏、超大、伪造和超时 `data.db` 的安全隔离。
- RBAC、TOTP、审计、软删除恢复及敏感字段加密。
- 公开端手机与桌面体验、后台桌面操作和 i18n 完整性。

## 7. 发布顺序

1. 内测验证三种结算包和社交列表身份字段。
2. 完成账号—角色—曾用名双层模型与本地身份库。
3. 打通插件绑定、身份同步和纷争前线上传。
4. 接入水晶冲突、烈羽争锋和关键时间线。
5. 完成网站查询、玩家档案、后台和匿名化。
6. 上线隔离的 `data.db` 导入。
7. 邀请测试阶段观察误合并率、身份同步量和隔离率。
8. 验证稳定后开放邮箱注册进入公测。

## 8. 首版明确不包含

- 用户自行修改战绩数据。
- 最近玩家动态和个人排行榜。
- 对外开放的第三方上传协议。
- 聊天记录、调试日志和逐技能原始遥测。
- UsedName 的昵称、查询、订阅、右键菜单和独立界面。
- 尚未确定的品牌视觉和具体前端页面布局。
